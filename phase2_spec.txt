# 3. BROWSERRUNTIME — GERENCIADOR CENTRAL DE NAVEGADOR

Criar um serviço central chamado:

`BrowserRuntime`

Responsabilidades:

- Inicializar Playwright.
- Inicializar Chromium.
- Manter o processo do navegador ativo durante a operação.
- Criar contextos independentes.
- Encerrar contextos individualmente.
- Recuperar sessões.
- Gerenciar páginas.
- Encerrar corretamente o navegador ao fechar a aplicação.

### Arquitetura desejada

```text
TKS ENGINE
│
└── BrowserRuntime
    │
    └── Chromium
        │
        ├── Contexto Conta 01
        │   └── TikTok Studio
        │
        ├── Contexto Conta 02
        │   └── TikTok Studio
        │
        ├── Contexto Conta 03
        │   └── TikTok Studio
        │
        ├── Contexto Conta 04
        │   └── TikTok Studio
        │
        ├── Contexto Conta 05
        │   └── TikTok Studio
        │
        └── Contexto Conta 06
            └── TikTok Studio
```

### Regras obrigatórias

Cada conta deverá possuir:

- Um BrowserContext exclusivo.
- Uma página independente.
- Cookies próprios.
- Estado de navegação próprio.
- Autenticação independente.

Nunca compartilhar cookies entre contextos.

Nunca reutilizar um contexto autenticado de uma conta para outra.

Não utilizar o perfil pessoal do Chrome.

Não abrir um novo processo Chromium para cada vídeo.

Reutilizar o contexto da conta durante sua fila ativa.

Quando não houver tarefas, permitir encerramento controlado do contexto para economizar memória.

Quando uma nova tarefa chegar, recriar o contexto utilizando as credenciais protegidas pelo DPAPI.

Preservar a possibilidade de recuperação de autenticação.

# 4. GERENCIAMENTO DO EVENT LOOP E PYQT6

A Playwright Async API deverá operar em um ambiente assíncrono consistente.

Antes de implementar, analisar a estrutura atual de `QThread` e `UploadWorker`.

Definir uma estratégia única para o ciclo de vida do Playwright.

Recomendação:

- Um worker dedicado para o runtime.
- Um event loop assíncrono pertencente a esse worker.
- Todos os objetos Playwright utilizados nesse loop.
- Comunicação com a GUI por sinais Qt.
- Nenhuma manipulação de objetos Playwright em threads externas.

Não compartilhar `Browser`, `BrowserContext` ou `Page` entre threads incompatíveis.

Não bloquear a interface gráfica.

Implementar encerramento gracioso, inclusive quando houver tarefas em andamento.

# 7. ROUND-ROBIN — DISTRIBUIÇÃO ALTERNADA

Implementar:

`RoundRobinRouter`

Cada departamento poderá ter várias contas TikTok.

A distribuição deverá ocorrer de forma alternada.

### Exemplo

Departamento 01 possui três contas:

- Conta A
- Conta B
- Conta C

Distribuição:

| Vídeo | Conta |
|---|---|
| Vídeo 01 | A |
| Vídeo 02 | B |
| Vídeo 03 | C |
| Vídeo 04 | A |
| Vídeo 05 | B |
| Vídeo 06 | C |

### Regras fundamentais

1. Cada vídeo será atribuído a uma única conta TikTok.
2. Nunca encaminhar automaticamente o mesmo vídeo para todas as contas.
3. Cada departamento terá seu próprio cursor.
4. A rotação deverá sobreviver a reinicializações.
5. Contas desativadas não poderão receber tarefas.
6. Contas não autenticadas deverão ser ignoradas temporariamente.
7. Contas com tarefas em andamento não poderão receber outra tarefa simultânea.
8. Se todas estiverem indisponíveis, manter o vídeo aguardando.
9. Não transferir automaticamente uma tarefa já atribuída após uma falha de submissão.

A seleção da conta e a atualização do cursor deverão acontecer dentro de uma transação SQLite.

Isso impedirá duas tarefas simultâneas de receberem a mesma posição da rotação.

### Importante

A lista de contas deverá ser obtida do AccountManager.

Não codificar nomes de usuários diretamente.

Não presumir que existe somente uma conta por departamento.

Permitir que o usuário associe várias contas ao mesmo departamento pela interface.

Preservar as associações atuais, tornando a ordem de distribuição configurável.

# 11. ISOLAMENTO E RECUPERAÇÃO

### Falha de uma conta

Se a Conta A perder a autenticação:

- Marcar `REAUTH_REQUIRED`.
- Pausar somente a Conta A.
- Preservar sua fila.
- Liberar a vaga de concorrência.
- Manter as demais contas operacionais.

### Falha de um contexto

- Encerrar somente o contexto afetado.
- Registrar o erro.
- Recuperar a sessão quando possível.
- Validar a identidade novamente.

### Falha do Chromium

- Identificar que o processo principal caiu.
- Suspender novas operações.
- Classificar tarefas interrompidas.
- Reinicializar o BrowserRuntime.
- Recriar contextos necessários.
- Preservar o estado das filas.

Se a submissão já tiver sido iniciada, mas não houver confirmação, classificar como `UNKNOWN`.

Não repetir automaticamente essa publicação.

### Reinicialização da aplicação

Ao abrir a TKS Engine:

1. Carregar as contas.
2. Carregar departamentos.
3. Carregar filas SQLite.
4. Recuperar cursores Round-Robin.
5. Identificar tarefas interrompidas.
6. Classificar operações em andamento.
7. Recuperar contextos sob demanda.
8. Retomar somente operações seguras.
